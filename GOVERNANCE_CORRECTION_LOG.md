| **03** | `PROJECT_SYSTEM_CONTRACT.md` §8.1 & `PROJECT_DECISION_REGISTER.md` PDR-021 | Stated: "Universal code language is ANSI/C99 C" and implied every question/solution is solved in C. | Not every question is a programming question. Furthermore, locking "ANSI/C99" prematurely was not approved. | **Rule 3.3:** **ALL CODE-BASED DSA IMPLEMENTATIONS USE C.** Theory $\rightarrow$ theory answer; Explain $\rightarrow$ explanation; Algorithm $\rightarrow$ algorithm; Pseudocode $\rightarrow$ pseudocode; Trace $\rightarrow$ dry run; Complexity $\rightarrow$ derivation; Programming $\rightarrow$ C program. Rule: *Standard, portable C; avoid compiler-specific extensions.* |
| **04** | `PROJECT_SYSTEM_CONTRACT.md` §7.3, §9.2 & `PROJECT_DECISION_REGISTER.md` PDR-027 | Stated: "Mastery requires 2–3 distinct sourced questions." | If the source corpus contains only 1 valid question for a specific family, requiring 2–3 questions would force the system to either invent synthetic questions (violating Rule 1) or leave the family unmasterable. | **Rule 9:** Mastery is **corpus-depth aware**. Desirable evidence is 2–3 questions when supported by corpus depth. If a family has only 1 valid question, **DO NOT invent questions**. Record: *"Insufficient corpus depth for multi-question mastery evidence."* |
| **05** | `PROJECT_SYSTEM_CONTRACT.md` §5 & `PROJECT_DECISION_REGISTER.md` PDR-012 | Required "mathematical proof" for every independent solution verification. | Most DSA university questions require algorithmic arguments, code analysis, dry-run state traces, or recurrence derivations. Requiring formal mathematical proof across all questions is academically mismatched. | **Rule 7:** Verification method depends on question type: algorithmic reasoning, code analysis, dry run, complexity derivation, mathematical reasoning, or structural reasoning. Correctness proofs only where genuinely applicable. |
| **06** | `PROJECT_SYSTEM_CONTRACT.md` §8.2 Trace & `PROJECT_PIPELINE.md` Phase 5 | Implied exhaustive tabular dry-run traces must be generated for all state-changing algorithms simply because they exist. | Overburdens students with redundant traces for standard definitions and algorithm descriptions that do not request a dry run. | **Rule 11:** Generate detailed tabular dry-run traces only when: (a) the sourced question explicitly asks for a trace/dry run, (b) the question requires explicit state transitions, or (c) it materially aids understanding of a sourced question. |
| **07** | `PROJECT_SYSTEM_CONTRACT.md` §8.3 & `PROJECT_DECISION_REGISTER.md` PDR-024 | Reduced all diagrams exclusively to hand-reproducible exam sketches and hard-coded diagram technologies (SVG, ASCII, KaTeX). | Students need rich, intuitive conceptual visualisations during learning, while needing clean, hand-reproducible diagrams for exam answer scripts. Furthermore, technology selection should not be prematurely locked in governance. | **Rule 12 & 15:** Maintain **two representations where useful**: **Learning View** (visually rich, detailed) and **Exam View** (technically correct, clear, fast to draw, hand-reproducible). Do not hard-code diagram rendering technologies in governance. |
| **08** | `PROJECT_SYSTEM_CONTRACT.md` §10.2 & `PROJECT_DECISION_REGISTER.md` PDR-033 | Included references to `IndexedDB`, PostgreSQL, and server-side relational databases. | The approved storage requirement is client-side browser storage without introducing unnecessary complexity. | **Rule 16:** Current implementation target is **`localStorage`**. Do not add IndexedDB, cloud storage, backend accounts, or sync unless explicitly decided in a later phase. State access layer remains abstract. |
| **09** | `PROJECT_SYSTEM_CONTRACT.md` §10.1 & `PROJECT_PIPELINE.md` Phase 10 | Prescribed frontend filenames (`index.html`, `app.js`, `style.css`) and frameworks (React, Vanilla JS). | Governance sets requirements, boundaries, and contracts—not framework choices. Premature stack locking restricts optimal technical architecture. | **Rule 17:** **DO NOT hard-code the frontend stack in governance.** Framework and tool selection belongs to Phase 9/10 architecture. |
| **10** | `PROJECT_SYSTEM_CONTRACT.md` §10.3 & `PROJECT_DECISION_REGISTER.md` PDR-037 | Stated arbitrary numeric performance targets: "Instant search response (<50 ms)". | Setting speculative millisecond thresholds prior to implementation and benchmarking is arbitrary and unverifiable at the contract phase. | **Rule 18:** Requirement is qualitative and rigorous: *"The full question corpus must remain responsive and usable on the target student environment."* Empirical benchmarks belong to implementation phases. |
| **11** | `PROJECT_SYSTEM_CONTRACT.md` §10.3 & `PROJECT_DECISION_REGISTER.md` PDR-036 | Described the Exam Sheet / Print View as a "handwritten-style" interface. | The print view should be a clean, high-clarity document stylesheet suitable for exam study and physical printing, not an artificial simulation of handwriting. | **Rule 19:** Clean **EXAM SHEET / PRINT VIEW** that strips site navigation and UI chrome while preserving complete answers, code, diagrams, and tables. Do not label as "handwritten-style". |
| **12** | `PROJECT_PIPELINE.md` Whole Document | Old pipeline had 11 phases with hard-coded references to "42 clauses" and lacked an explicit Authoritative Syllabus Extraction phase. | Authoritative syllabus extraction must occur before topic gating to avoid topic hallucination.
